Integration Overview

Three integration surfaces.

ROUA exposes three distinct surfaces. Each returns evidence-linked intelligence — the difference is latency, format, and use case.

{ }
REST API · representative
Synchronous request/response for on-demand intelligence queries — source lookups, fact retrieval, evidence chain pulls, intelligence module outputs. Every response carries provenance: source document, page, paragraph, extraction confidence. Full specification shared during onboarding.
→
Streaming (WebSocket) · integration roadmap
Real-time push of events as they are detected and validated — new source publications, fact extractions, risk alerts, intelligence updates. For dashboards, alerts, and live workflows that must react as the registry moves. Available by deployment model.
</>
SDK + Components · integration roadmap
Typed SDK (TypeScript / Python) wrapping the REST and streaming surfaces, plus embeddable UI components for evidence cards, source citations, and intelligence briefs. Planned for supported integration environments — availability confirmed during onboarding.
Authentication

How your requests are authenticated.

ROUA uses scoped API keys issued per institution, per environment. Keys are not shared across staging and production. Every request is auditable back to the issuing credential.

@
Scoped API Keys
Keys carry explicit scopes — which intelligence products, which source tiers, which endpoints. A key cannot read beyond its scope. Scopes are reviewed during onboarding and adjustable per environment.
🔒
TLS + Bearer Token
All traffic over TLS 1.2+. Authentication via Bearer token in the Authorization header. No basic auth, no query-string secrets. Key rotation and revocation configured per environment.
📋
Per-Request Audit
API requests are logged with credential, scope, endpoint, timestamp, and applicable source/evidence references. Audit logs are available to your institution's security and compliance teams — not just to ROUA operators.
API Surface

Representative endpoint surface.

The endpoints below are representative and illustrative — not a production API contract. The full specification is shared with engineering teams during onboarding, not published openly. Each endpoint is designed to return evidence-linked output, not raw data.

GET
/v1/sources
List monitored sources by tier, jurisdiction, or type. Returns source registry entries with trust tier and last-checked status.
scope: sources:read
GET
/v1/sources/{source_id}/documents
Retrieve documents ingested from a specific source. Each document includes ingestion timestamp, parse status, and paragraph-level anchors.
scope: sources:read
GET
/v1/facts?entity={entity_id}
Retrieve extracted facts for an entity. Each fact carries source document, page, paragraph, extraction confidence, and validation status.
scope: facts:read
GET
/v1/evidence/{evidence_id}
Pull the full evidence chain for a specific intelligence output — from source document through validation to the derivation trace that produced it.
scope: evidence:read
POST
/v1/intelligence/investment/brief
Request an Investment Intelligence brief for a given entity or theme. Returns a structured brief with embedded evidence references, not free text.
scope: intelligence:investment
POST
/v1/intelligence/risk/scan
Run a Risk Intelligence scan against a portfolio or exposure set. Returns flagged risks with source citations and confidence scores.
scope: intelligence:risk
WS
/v1/stream/events
WebSocket subscription for real-time event pushes — new source publications, fact extractions, risk alerts. Filterable by entity, source tier, or event type.
scope: stream:events

Endpoint paths and scopes shown above are representative. The full OpenAPI 3.1 specification, including request/response schemas, pagination, rate limits, and error codes, is provided to engineering teams under NDA during onboarding.

Evidence Access

Every response is evidence-linked.

This is the difference between ROUA and a generic data API. Every intelligence response includes structured provenance your downstream systems — and authorized reviewers — can inspect.

🔗
Source Anchors
Every fact carries a source anchor: document identifier, page, paragraph. Not a URL to a homepage — a structural reference into the original document your compliance team can pull on demand.
⚙
Confidence Signals
Extraction confidence, source trust tier, and validation status travel with every fact. Your downstream code can filter, threshold, or flag based on these signals — not assume all facts are equal.
📝
Derivation Trace
Intelligence outputs include a derivation trace — which facts were used, which rules were applied, which validation gates passed. The "how" is part of the response, not a separate audit log.
📊
Evidence Chain Pull
For any intelligence output, the full evidence chain is retrievable via a single endpoint — source → document → fact → validation → evidence → derivation → output. Traceable by construction.

  -H "Content-Type: application/json" \
  -d '{
    "entity": { "ticker": "NVDA" },
    "scope": "earnings_analysis",
    "evidence_depth": "full"

Integration Architecture

How the integration fits your stack.

ROUA does not replace your data warehouse, your OMS, or your editorial CMS. It sits alongside them as an intelligence layer — queried on demand, pushed via stream, or embedded via SDK.

⚙
Behind Your Stack
ROUA is called from your existing services — research workflows, risk engines, editorial tools — not placed in front of them. Your systems own the user experience; ROUA supplies the evidence-linked intelligence.
🔌
Versioned Retrieval
Retrieval endpoints are cacheable by immutable evidence/object identifiers — the same governed object version resolves to the same evidence snapshot. Generation endpoints use request identifiers for traceability.
📱
Typed SDK · planned
TypeScript and Python SDKs with full type definitions for request and response shapes. Planned for supported integration environments — availability confirmed during onboarding.
📦
Embeddable Components
For teams building internal tools: embeddable evidence cards, source citation widgets, and brief renderers. Drop a ROUA evidence card into your research portal without rebuilding the brief UI.
🛡
Private Deployment
For institutions that cannot send intelligence queries over the public API: ROUA can be deployed inside your environment — same API surface, same evidence model, your network boundary.
📊
Observable
Structured logs, metrics, and traces available to your observability stack. Request IDs propagate end-to-end — from your service through ROUA's pipeline to the source document.

API Access

Request API access.

ROUA does not publish a public sandbox or self-serve API keys. API access is provisioned through institutional onboarding — because every key carries product scopes, source-tier access, and audit obligations that must be configured for your institution.

What onboarding includes

API access is not a sign-up form. It is a structured onboarding that aligns the API surface with your institution's intelligence products, source-tier permissions, security review, and audit requirements. The onboarding timeline is determined by integration scope and institutional security requirements.

  • Scope alignment — which intelligence products, which source tiers, which endpoints your institution will access
  • Environment provisioning — staging keys for integration development, production keys for live deployment
  • OpenAPI 3.1 specification — the full schema, request/response shapes, pagination, rate limits, error codes
  • SDK access — TypeScript and Python SDKs with type definitions and integration examples (availability confirmed during onboarding)
  • Security review — credential rotation, audit log access, network and deployment options
  • Engineering briefing — a working session with your integration team on evidence access patterns and best practices
How to start

If your institution has already engaged ROUA through a product briefing, contact your institutional lead and ask to be connected to the developer onboarding team. If you have not yet engaged ROUA, the first step is a product briefing — API access follows institutional engagement, not the other way around.

Enterprise Integration

For institutions with stricter boundaries.

Banks, sovereign funds, and regulated institutions often cannot send intelligence queries over a public API. ROUA supports deployment models that keep the intelligence layer inside your boundary — without changing the integration surface.

🛡
Private Deployment
ROUA deployed inside your environment — same API surface, same evidence model, same SDK. Your engineers integrate against a local endpoint; no intelligence query leaves your network.
🔒
Dedicated Source Tiers
For private deployments, source tiers can be scoped to your institution's licensed sources — your API keys cannot reach beyond what your institution has rights to access.
📋
Your Audit Trail
Audit logs stay inside your environment. Every API call, every evidence pull, every intelligence output — logged to your SIEM, not to ROUA's cloud.
🤝
White-Label Presentation
For media and data companies building customer-facing products on ROUA: white-label presentation with your brand and editorial layer — with source attribution and provenance preserved. Trust requires provenance to remain visible.
